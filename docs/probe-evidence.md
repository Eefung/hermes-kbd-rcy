# 探针实测证据

本文件记录 `tools/kbdprobe.py` 在真实终端中测到的原始结果。所有数字都来自 `CSI ? u` 查询:探针把 stdin 置为 raw 模式,向 `/dev/tty` 写 `CSI ? u`,读取终端应答 `CSI ? flags u`;配合 `1049h` / `1049l` 切换屏幕,即可**分别查询主屏与 alt 屏的 flags**。

## 环境

| 项 | 值 |
|---|---|
| 系统 | CachyOS(Arch 系),内核 7.3.3-1-cachyos |
| 会话 | KDE Plasma,Wayland |
| 终端 | kitty 0.49.2 |
| shell | fish 4.9.3 |
| 肇事程序 | hermes-agent v0.23.0(2026.9.24),`hermes --tui` |
| 日期 | 2026-11-10 |

## 实验一:两屏协议栈是否独立

先在主屏 push,再进出 alt 屏,观察两屏各自的 flags:

| 步骤 | 查询屏 | 结果 |
|---|---|---|
| 基线 | 主屏 | 0 |
| 主屏 push `CSI > 1 u` | 主屏 | 1 |
| 进入 alt 屏(`1049h`) | alt 屏 | **0** —— 不继承主屏 |
| 退出 alt 屏(`1049l`) | 主屏 | 1 —— 主屏状态原样保留 |

结论:两屏的协议栈完全独立,进入 alt 屏不会复制主屏的 flags,退出也不会重置主屏。

## 实验二:残留与复现(肇事程序的真实顺序)

hermes TUI 先挂 alt 屏、后设置 raw 模式,因此 push 发生在 **alt 屏内**。探针按这个顺序复现:

| 步骤 | 查询屏 | 结果 |
|---|---|---|
| alt 屏内 push `CSI > 1 u`,随后退出 alt(不 pop) | alt 屏 | 1 |
| 退出 alt 后 | 主屏 | **0** —— 主屏毫无征兆 |
| 重新进入 alt 屏(= micro / vim 的视角) | alt 屏 | **1 —— 残留复现** |

这正是「提示符正常、编辑器全坏」的原因:编辑器进入的 alt 屏带着 flags = 1。

## 实验三:旧的单屏清理为何无效

在实验二的残留状态下,从**主屏**(shell 提示符)发送旧清理序列 `\e[<u`×3 + `\e[=0u`:

| 步骤 | 查询屏 | 结果 |
|---|---|---|
| 主屏发旧清理 | 主屏 | 0(主屏本身被清掉) |
| 再进入 alt 屏 | alt 屏 | **仍是 1 —— 无效** |

结论:清理序列只作用于当前所在屏;从提示符下发,永远碰不到 alt 栈。这也解释了为什么大量用户报告「手敲 pop/清零序列不起作用,只有 reset 行」。

## 实验四:两屏清理验证

清理序列:`1049h` → `<u`×3 + `=0u` → `1049l` → `<u`×3 + `=0u` → `>4m` → `1004l` → `2004l` → `25h`。

| 场景 | 清理后主屏 | 清理后 alt 屏 |
|---|---|---|
| alt 屏内 push ×1 后退出,再从主屏清理 | 0 | **0** |
| alt 屏内 push ×2(更深栈)后退出,再从主屏清理 | 0 | **0** |

两种深度都能清干净:多余 pop 对空栈是无害 no-op,`=0u` 与栈深度无关。

## 实验五:`reset` 的有效成分

为什么 `reset` 总能修好,而定向序列(在某些中间层下)不行?看 kitty 的 terminfo:

```
rs1=\E]\E\\\Ec
```

`rs1` 的结尾是 **RIS(`ESC c`)**——全量复位,连两屏的协议栈、alt 屏状态、termios 一并重置。`reset` 的有效性来自这颗核弹,而非它「弹了栈」。这也划定了本仓库清理序列的边界:它只处理键盘协议栈和几个可安全复位的小模式(focus 上报、bracketed paste、光标可见性),不做全量复位;遇到 tmux / ssh kitten 这类自持状态的中间层,仍需 `reset` 兜底。

## 附加观察:modifyOtherKeys 不会映射到 flags

`CSI > 4;2m`(xterm modifyOtherKeys = 2)在 kitty 中不会反映到 `CSI ? u` 查询里(查询结果保持 0);kitty 只是为兼容性接受该序列。因此 `113;5u` 症状本身来自协议栈 flags,而非 modifyOtherKeys——这也是清理序列里 `>4m` 只作为防御性复位、真正解决问题的是两屏弹栈的原因。

## 方法论备注

- 序列必须写入 `/dev/tty`(重定向 stdout 会吞掉转义序列,得到「查询全空」的假象)。
- 查询前先 `tcflush` 输入队列,读应答用 select 超时,避免残留应答串扰。
- `--simulate` 会真的把 alt 栈弄脏(这是复现手段),请配合 `--fix` 或手动清理序列使用。

复现全部实验:

```sh
python3 tools/kbdprobe.py --simulate --fix
```
